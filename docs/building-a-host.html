You already have a chat app

The four pieces you build

You have a chat window, a backend and an AI model that can call tools. To show MCP Apps, you extend two things you already have and add two new ones. The SDK handles the hard protocol work.

Piece 1 · extend

Backend

Connects to MCP servers, hides tools the AI shouldn't see, tells the browser "this tool has a screen", and forwards the app's requests.

Piece 2 · new

Sandbox page

One tiny HTML page on a separate domain. It holds the app in a sealed frame and passes notes through.

Piece 3 · new

AppFrame

A component in your chat bubble. It creates the iframe and an AppBridge, then runs the startup steps in order.

Piece 4 · extend

Chat logic

Lets the app write into the chat and tell the AI what it is showing.

Know your guest

An MCP App has two halves

The app's author writes both halves of an MCP App, usually in one project, but the halves run in different places. The server half runs on a server. The UI half is stored on that server and runs in the person's browser, inside your sandbox.

Server half · server.ts

A tool and a screen, tied by one URI

registerAppTool(server, "get-time", {
  inputSchema: z.object({}),
  _meta: { ui: { resourceUri: "ui://get-time/mcp-app.html" } },
}, async () => ({
  content: [{ type: "text", text: time }],
  structuredContent: { time },
}));

registerAppResource(server, uri, uri,
  { mimeType: RESOURCE_MIME_TYPE },
  async () => ({ contents: [{ uri,
    mimeType: RESOURCE_MIME_TYPE,
    text: await readFile("dist/mcp-app.html") }] }));

UI half · src/mcp-app.ts

Waits for your host, then draws

const app = new App({ name: "Get Time App", version: "1.0.0" });

// register handlers before connect()
app.ontoolinput  = (p) => showLoading(p.arguments);
app.ontoolresult = (r) => show(r.structuredContent);
app.onhostcontextchanged = applyTheme;
app.onteardown   = async () => { save(); return {}; };

button.onclick = () =>
  app.callServerTool({ name: "get-time", arguments: {} });

await app.connect();  // sends ui/initialize to your AppFrame

Text and data

A tool result has content (text the model reads) and structuredContent (data the UI draws). Pass the whole result to the app.

Text first

The server half calls getUiCapability() on your client's capabilities. If your host didn't advertise the extension, it may register a text-only tool instead.

React too

React apps use useApp(), useHostStyles() and useAutoResize() from /react. On the wire it's the same protocol.

You build the host. The app's author builds both halves. You only meet the UI half, through postMessage.

Piece 1

Backend: notice the screen

Your AI loop already calls tools. Now it checks one extra thing: does this tool come with a screen? If yes, it tells the browser.

Four jobs

Job 1 · connect

Say you support apps

When your MCP client connects, advertise the extension. Then list tools and resources once and keep them.

capabilities: { extensions: {
  "io.modelcontextprotocol/ui": {
    mimeTypes: ["text/html;profile=mcp-app"]
  } } }

Job 2 · filter

Hide app-only tools from the AI

If a tool's _meta.ui.visibility leaves out "model", don't give it to the model. It is a button for the app, like "refresh".

Helpers: isToolVisibilityAppOnly(tool) and getToolUiResourceUri(tool) from @modelcontextprotocol/ext-apps/app-bridge.

Job 3 · stream

Tell the browser

  • app-starttoolCallId, server, toolName, args, resourceUri
  • app-args-partialoptional, while the model is still typing the arguments
  • app-result or app-cancelledwhen the tool call finishes or fails

Job 4 · proxy

Endpoints for the app

  • GET /api/apps/resourcereads the ui:// resource, checks the MIME type, returns { html, csp, permissions }
  • POST /api/apps/tools/callforwards, but refuses tools whose visibility leaves out "app"
  • POST /api/apps/resources/readforwards as is

Also save toolName, args, uri and result with the message, so the app can be redrawn when the chat is reopened.

Piece 2

A separate home for strangers

The app's HTML was written by someone else. If it ran on your domain, it could read your cookies and your chat. So it runs on a different domain, inside a glass room.

What sandbox.html does, about 130 lines

  1. Refuses to run unless it is inside an iframe and the parent's origin is yours.
  2. Creates the inner iframe with sandbox="allow-scripts allow-same-origin allow-forms".
  3. Tells the parent it is ready: ui/notifications/sandbox-proxy-ready.
  4. When ui/notifications/sandbox-resource-ready arrives, writes the HTML into the inner iframe and sets its allow permissions.
  5. Passes every other note both ways, always naming the exact target origin, never *.

The sandbox server

Serves sandbox.html with a Content-Security-Policy header built from the ?csp= value. Check every domain in it so nobody can sneak in extra rules with ; or quotes.

Copy, don't invent

examples/basic-host/src/sandbox.ts and serve.ts already do all of this. Change the allowed origin to your domain.

Piece 3

Showing the app, step by step

Here is the whole trip, from you typing a question, through the model choosing a tool, to a working screen and the model's answer. Press Play to watch it one stage at a time.

    Overview

    One question becomes a screen

    All 25 arrows are drawn at once. Press Play to watch them one at a time.

    
        
    
      
    
      
    
      
    Left band: what runs in the person's browser. Right band: servers. Any arrow that crosses the gap between the bands goes over the network, and its label sits in that gap. The two MCP App lanes are one app split in two: its server half runs on a server, and its UI half is HTML that the server hands over and the browser runs, like any web page. The tags give each lane's MCP role: HOST is everything you build, including your backend; VIEW is the app's UI; SERVER is the app's MCP server. Filled head: someone waits for an answer. Open head: one-way. Once the app is running, every note passes through the sandbox page untouched.
    

      
    The same stages in code
    

    import { AppBridge, PostMessageTransport } from "@modelcontextprotocol/ext-apps/app-bridge";

async function mountApp(iframe, call, chat) {
  // Fetch the screen: HTML + CSP from your backend
  const ui = await api.getAppResource(call.server, call.resourceUri);

  const bridge = new AppBridge(null, { name: "my-chat", version: "1.0.0" },
    { serverTools: {}, serverResources: {}, openLinks: {}, updateModelContext: { text: {} } },
    { hostContext: {
        theme: currentTheme(), platform: "web", displayMode: "inline",
        availableDisplayModes: ["inline", "fullscreen"],
        containerDimensions: { maxHeight: 6000 },
        styles: { variables: myCssVariables },
    } });

  // Register every handler BEFORE connect()
  bridge.oncalltool           = (p) => api.callTool(call.server, p);
  bridge.onreadresource       = (p) => api.readResource(call.server, p);
  bridge.onmessage            = async (p) => { chat.sendAsUser(p); return {}; };
  bridge.onupdatemodelcontext = async (p) => { chat.setAppContext(call.toolCallId, p); return {}; };
  bridge.onopenlink           = async ({ url }) => { window.open(url, "_blank", "noopener"); return {}; };
  bridge.onsizechange         = ({ height }) => { if (height) iframe.style.height = `${height}px`; };
  bridge.onrequestdisplaymode = async ({ mode }) => { chat.setFullscreen(call.toolCallId, mode === "fullscreen"); return { mode }; };
  const initialized = new Promise((r) => (bridge.oninitialized = () => r()));

  // Build the glass room: load sandbox.html?csp=... and wait for proxy-ready
  await loadSandboxProxy(iframe, ui.csp, ui.permissions);
  // connect: target AND source are this iframe, so other windows are ignored
  await bridge.connect(new PostMessageTransport(iframe.contentWindow, iframe.contentWindow));
  // ...then hand over the HTML
  await bridge.sendSandboxResourceReady({ html: ui.html, csp: ui.csp, permissions: ui.permissions });
  // Say hello: AppBridge answers ui/initialize for you
  await initialized;
  // Send the data
  bridge.sendToolInput({ arguments: call.args });
  call.result.then((r) => bridge.sendToolResult(r),
                   (e) => bridge.sendToolCancelled({ reason: String(e) }));
  return bridge;
}

// When the bubble unmounts
await bridge.teardownResource({});   // lets the app save, then remove the iframe

    Piece 4
    
      
    How the UI and the model stay in touch
    
      
    After the first render, the UI can't reach the model directly. Everything goes through your host, by one of four routes, and your host decides what the model gets to see.
    
      
    
      
    

      
    
        
    
          
          
          
          
          
      
        
      
        
      
          
      Overview
      
          
      Four routes, one gatekeeper
      
          
      
          
      All four routes are drawn at once. Press Play to watch them one arrow at a time.
      
          
      
        
      
      
      
      
      
      
      "Your host" is your chat UI, AppFrame and backend together; the AppBridge inside the AppFrame handles every arrow between the app and your host. The dashed line in route 1 marks time passing: the context update has been saved, but the model hasn't seen it yet.
      

      
      Who picks the route?
      
      
      The app's developer, one button at a time. Each click handler calls a different SDK method, each method sends a different message, and AppBridge hands it to a different handler. Your host never guesses.
      
      
      
        
      
          
      ButtonApp callsYour host getsResult
      
          
            
      RefreshcallServerTooltools/call → oncalltoolThe tool runs on the server. The model isn't involved.
      
            
      Explain thissendMessageui/message → onmessageA new user turn starts now.
      
            
      (panned the map)updateModelContextui/update-model-context → onupdatemodelcontextSaved for the next turn.
      
                
        
      
      
      
      
      Your host can't change the route, but it can refuse one: reject the message, block tools without "app" visibility, or leave message or serverTools out of its capabilities.
      

      
      What makes your host list the app's tools? (route 4)
      
      
      
        
      1 · The handshake
      The app's ui/initialize includes the tools capability. registerTool adds it for you. When oninitialized fires, check bridge.getAppCapabilities()?.tools and call bridge.listTools(). No capability, no route 4.
      
        
      2 · The tools change
      If the app declared tools.listChanged, it sends notifications/tools/list_changed whenever it adds, removes or changes a tool. registerTool sends it for you. List again and replace what you offer the model.
      
      
      
      
      The model and the person never trigger it directly. The model can't ask for tools it hasn't been shown. You can list right away or just before the next model request. Keep one list per screen, keyed by toolCallId, and drop it at teardown.
      

      
      What the model sees, and what it doesn't
      
      
      
        
      The model sees
        
          
      • The tool result's content (text, and images if it has them)
        • 
          
      • ui/message, as a user message, straight away
        • 
          
      • The latest updateModelContext, on the next turn
        • 
          
      • Results of the app's own tools that the model itself called
        • 
        
      
        
      The model never sees
        
          
      • The tool result's structuredContent and _meta: those are for the UI
        • 
          
      • Tools the UI calls with callServerTool, or their results
        • 
          
      • Logs from sendLog
        • 
          
      • Clicks, scrolls, typing, anything the app doesn't report
        • 
          
      • Older context updates that a newer one replaced
        •

      Keep it small
      Context costs tokens. Apps send short markdown, often with YAML frontmatter. map-server adds a screenshot only if your host declares updateModelContext.image, scaled to 768 px.
      
        
      Latest wins
      If several updates arrive before the next user message, send only the last one. An empty update can clear the slot, as basic-host does.
      
        
      Many apps, many slots
      Keep one slot per app instance (use toolInfo.id) and label each one, so the model knows which map moved.
      
      
      
      
      Rule of thumb: updateModelContext says "here is what I'm showing". sendMessage says "please do something now".

      A screen's life
      
      
      

      
      When the chat is reopened
      
      
        
        
      1. Load the saved message: tool name, arguments, result and resourceUri, plus the latest model context if you keep it.
        2. 
        
      2. Mount a fresh AppFrame and sandbox, and get the HTML again (a cache is fine; the HTML is declared up front).
        3. 
        
      3. Handshake as usual, then send tool-input and tool-result from the saved copy. Replaying avoids running the tool, and its side effects, twice.
        4.

        5.

      Permissions, CSP and sign-in
      
      
      The server half says what its UI needs. Your host decides what to allow and enforces it in the sandbox.

      Real apps
      
      
      Patterns your host must handle
      
      
      These come from the patterns guide and the example apps. Each one needs a little support from your host.
      
      
      
        
      pdf-server · system-monitor-server
      Buttons that call hidden tools
      Tools with visibility: ["app"] power refresh buttons, polling and paging. Let them through oncalltool, and keep them out of the model's tool list.
      
        
      pdf-server
      Big files in pieces
      If you cap tool-result size, apps fetch large files in chunks through an app-only tool. Don't rate-limit those repeated calls away.
      
        
      shadertoy-server · threejs-server
      Streaming arguments
      Send tool-input-partial while the model types. Close any open brackets first so it parses ("healed" JSON). Apps use it for previews only.
      
        
      transcript-server
      Big follow-ups
      The app sends a long text through updateModelContext, then a short prompt through sendMessage. Store the context before you start the model turn.
      
        
      pdf-server · map-server
      Remembering where you were
      A tool result can carry _meta.viewUUID, and the app saves state in localStorage under it. Keep your sandbox origin stable, and send the same saved result when you redraw the chat.
      
        
      any app
      Errors
      The server half returns isError: true and the model reads it. The UI reports problems found later through updateModelContext.
      
        
      shadertoy-server · threejs-server
      Offscreen apps
      Heavy apps pause themselves with IntersectionObserver. In long chats you can also tear down apps that scrolled far away.
      
        
      debug-server
      Close, download, ask the model
      requestTeardown asks you to close it, so call teardownResource if you agree. downloadFile exists because the sandbox blocks downloads. createSamplingMessage asks your model directly, only if you declare sampling.
      
      
      
    
      

    
    
      
      
      Test yourself
      
      
      Questions an expert can answer
      
      
      These are the questions to ask when you build both an app and a host. If you can answer them all, you understand MCP Apps from both sides.
      
      
      
        
      
          
      Rendering
      
          
      
            
      Where does the HTML come from, and when should I fetch it?
      
            
      From the app server's ui:// resource via resources/read. Resources are declared up front, so you may fetch and cache them when you connect. Data arrives later, as tool input and result.
      
            
      Do I need the SDK?
      
            
      No. It's JSON-RPC 2.0 over postMessage. App and AppBridge save you the bookkeeping and type checking.
      
            
      Why two iframes?
      
            
      On the web, the app must run on a different origin from your chat so it can't read your cookies or page. The middle sandbox page provides that origin and passes messages through. Desktop hosts may use one sandboxed frame.
      
            
      Can two copies of the same app be on screen?
      
            
      Yes, one per tool call, each with its own iframe and AppBridge. toolInfo.id and viewUUID tell them apart. Apps can't talk to each other; the spec lists that as future work.
      
            
      What if a host doesn't support MCP Apps?
      
            
      The tool still works and the person sees its content as text. Servers can check getUiCapability() and register a text-only tool instead.
      
          
      
        
      
        
      
          
      The model
      
          
      
            
      What does the model see from a tool result?
      
            
      content only. structuredContent and _meta are for the UI.
      
            
      How does the model learn what I did in the UI?
      
            
      Only if the app tells it: updateModelContext (quiet, next turn, latest wins) or sendMessage (a user message, now). The app's own tool calls stay invisible.
      
            
      Can the model operate the UI?
      
            
      Yes, if the app registers tools with app.registerTool() and your host offers them to the model through bridge.listTools() and bridge.callTool().
      
            
      Can the app call the model directly?
      
            
      With createSamplingMessage, if you declare sampling and handle oncreatesamplingmessage.
      
            
      Can the app see the chat?
      
            
      No. It only gets what you send: tool input and result, host context, and replies to its own requests.
      
          
      
        
      
        
      
          
      State
      
          
      
            
      What happens when the chat reloads?
      
            
      The iframe is new and its memory is gone. You mount it again and replay the saved input and result; the app restores the rest from localStorage or its server.
      
            
      Should I save model context?
      
            
      You should give the latest one to the model on future turns. Saving it with the conversation keeps it across reloads. That part is your choice.
      
            
      Where should the app keep work the person can't lose?
      
            
      On its server, through app-only tools, scoped by viewUUID or user. localStorage suits small view details like page number or camera position.
      
          
      
        
      
        
      
          
      Safety and operations
      
          
      
            
      Can an app call any tool?
      
            
      Only tools on its own server whose visibility includes "app". You must reject others, and calls across servers are always blocked for app-only tools.
      
            
      Can an app reach the internet?
      
            
      Only the domains in its _meta.ui.csp. With no CSP it gets strict defaults and can't reach anything.
      
            
      How do I debug?
      
            
      Run examples/basic-host: it has Tool Input, Tool Result, Messages and Model Context panels, and logs [HOST] lines in the console. debug-server exercises every capability.
      
            
      I have an OpenAI Apps SDK app. Now what?
      
            
      docs/migrate_from_openai_apps.md maps window.openai to App methods. The migrate-oai-app skill in plugins/mcp-apps walks through it.
      
          
      
        
      
      
      
    
      

    
    
      
      
      Plan the work
      
      
      Build it in this order
      
      
      Each step gives you something you can see working before you start the next one.
      
      
      
      
        
        
      1. Backend events. Connect with the extension, filter tools, stream app-start and app-result. Log them; no UI yet.
        2. 
        
      2. Sandbox origin. Serve sandbox.html on a second port or domain with the CSP header.
        3. 
        
      3. Show the app. AppFrame with tool input, tool result and resizing. Test with the examples/basic-server-* servers; npm start in this repo runs them all.
        4. 
        
      4. Talk back. Add onmessage, onupdatemodelcontext, onopenlink and theme changes.
        5. 
        
      5. Polish. Fullscreen and picture-in-picture, teardown, redrawing apps from saved chats, permission prompts, and tearing down iframes that scroll far away.
        6.

      Checklist
      
      
      "Must" items come from the spec. "Should" items are what makes it feel finished.
      
      
      
        
      
          
      ItemWhereLevel

      CSP built from the resource's ui.csp, strict when missingSandbox serverMust
      
            
      Nothing sent to the app before initializedAppFrameMust
      
            
      tool-input sent after the handshakeAppFrameMust
      
            
      App-only tools hidden from the modelBackendMust

      Advertise io.modelcontextprotocol/ui on connectBackendMust
      
            
      teardownResource before removing an iframeAppFrameShould

      Your CSS variables passed in hostContext.stylesAppFrameShould
      
            
      Apps redrawn from saved chat historyBackend + chatShould
      
            
      Only declare capabilities you actually handleAppFrameShould

      Tool call retried after OAuth when the server answers 401BackendShould
